이 페이지는 Sui에서 application을 개발할 때 권장되는 몇 가지 보안 모범 사례를 설명한다. 이 권장 사항은 모든 application type, use case, architecture를 포괄하지 않는다. 직접 조사하고 production application은 철저히 audit받는 것을 권장한다.

## 스마트 컨트랙트 보안

#### 컨트랙트 감사

transaction이 신뢰하고 audit한 smart contract에서 동작하는지 확인한다. Sui smart contract는 수정을 방지하기 위해 immutable object로 정의된다.

#### random call은 PTB에서 마지막이어야 한다

이는 attacker가 결과를 inspect하고 불리하면 abort하는 `test-and-abort` attack을 방지한다.

#### 함수를 entry로 표시

다른 Move module이 randomness-consuming function을 예기치 않게 호출하지 못하도록 한다.

#### `RandomGenerator`를 parameter로 받지 않기

manipulation을 방지하기 위해 generator는 항상 내부에서 생성한다.

#### outcome path 간 가스 균형 맞추기

모든 outcome이 비슷한 gas를 소비하도록 function을 설계해, attacker가 유리한 outcome에서만 성공하는 gas budget을 설정하지 못하도록 한다.

#### high-stakes application에는 two-transaction commit-reveal pattern을 고려한다.

## Seal (암호화 및 접근 제어)

신뢰할 수 있는 key server operator를 선택하고 organization, jurisdiction, infrastructure provider 전반에 분산한다.

availability를 유지하면서 compromised server를 tolerate하려면 threshold encryption(예: 2-of-3)을 사용한다.

sensitive 또는 large data에는 envelope encryption을 사용한다. 자체 symmetric key로 data를 encrypt한 뒤, Seal은 해당 key에 대한 access만 관리하는 데 사용한다.

#### 올바른 access policy 보장

`seal_approve*` function의 Move code는 의도한 access rule을 정확히 표현해야 한다. upgradeable package는 언제든 policy change를 허용한다.

## Nautilus

#### enclave code 최소화

code가 적을수록 attack surface가 작아진다.

#### dependency audit

enclave에서 사용하는 모든 library를 review한다.

#### 짧은 timestamp 사용

replay attack window를 줄인다.

#### PCR monitoring

예기치 않은 PCR value에 대해 alert한다.

#### TEE guarantee에만 의존하지 않는다.

## Coin 및 capability 보안

#### TreasuryCap 보호

이는 minting 및 burning permission을 제어한다.

#### MetadataCap 보호

이는 coin branding을 제어한다.

#### DenyCapV2 보호

이는 coin usage를 제한할 수 있다.

#### supply model을 일찍 설정하고 fixed, burn-only, flexible supply의 의미를 이해한다.

## key management

#### private signature key를 비공개로 유지한다.

이 key 없이는 다른 party가 사용자의 owned asset에 대해 operation을 수행할 수 없다.

#### recipient address를 주의 깊게 verify한다.

object를 잘못된 address로 보내면 되돌릴 수 없는 영향을 줄 수 있다.
